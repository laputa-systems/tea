Implement a first-class persistent nested todo builtin.

This should take inspiration from:

* `fitchmultz/pi-todo-list` for durable nested todo semantics;
* Oh My Pi (`omp`) for coding-agent ergonomics and compact progress presentation;

but the resulting design should be much simpler for the model than either implementation.

The central design principle is:

> **Push complexity into the todo tool. Make the model-facing interface almost trivial.**

And the central implementation principle is:

> **The todo system is a Luau extension. Rust provides only generic extension persistence and generic presentation plumbing.**

Use the existing builtin:

```text
crates/tea-luau/builtins/goal/
```

as the architectural precedent.

Do not build a Rust todo subsystem.

---

# 1. Desired UX

The model should basically understand only two concepts:

1. read the current todo document;
2. report status changes.

Structural editing should be exceptional and happen by submitting a replacement Markdown tree, not through CRUD operations.

There should be:

* no `op` enum;
* no `add`;
* no `move`;
* no `remove`;
* no `complete`;
* no `reopen`;
* no `batch`;
* no `parent_id` exposed to the model;
* no tree traversal exposed to the model;
* no pagination exposed to the model.

The model should never need to understand the internal todo representation.

The extension does all of that work.

The model-facing tool is simply:

```text
todo
```

with approximately this schema:

```json
{
  "type": "object",
  "properties": {
    "markdown": {
      "type": "string",
      "description": "Full desired todo tree. Use only when creating or restructuring the plan."
    },
    "updates": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["id", "status"],
        "properties": {
          "id": {
            "type": "integer",
            "minimum": 1
          },
          "status": {
            "enum": [
              "pending",
              "in_progress",
              "done",
              "blocked",
              "dropped"
            ]
          },
          "reason": {
            "type": "string"
          }
        },
        "additionalProperties": false
      }
    }
  },
  "additionalProperties": false
}
```

The handler should enforce:

```text
{}                      -> read
{ markdown = "..." }    -> synchronize structure
{ updates = [...] }     -> update statuses
```

Reject providing both `markdown` and `updates` in the same call.

That is the complete model-facing conceptual API.

---

# 2. The normal interaction

Typical model behavior should look like this.

At the beginning of substantial work:

```json
{}
```

If no plan exists, the model can establish one:

```json
{
  "markdown": "- [ ] Implement todo extension\n  - [ ] Luau state machine\n  - [ ] Durable host integration\n  - [ ] Spinner integration\n  - [ ] Verification"
}
```

The tool assigns stable IDs and returns:

```text
TODO · 1 active · 3 pending · 0 blocked · 0 dropped · 0 done

- [ ] #1 Implement todo extension
  - [>] #2 Luau state machine
  - [ ] #3 Durable host integration
  - [ ] #4 Spinner integration
  - [ ] #5 Verification
```

After finishing #2:

```json
{
  "updates": [
    {
      "id": 2,
      "status": "done"
    }
  ]
}
```

The extension:

* marks #2 done;
* observes there is no remaining active item;
* automatically promotes the next pending actionable leaf;
* persists state;
* updates the spinner presentation;
* returns something concise such as:

```text
Completed #2.
Next: #3 Durable host integration
TODO · 1 active · 2 pending · 0 blocked · 0 dropped · 1 done
```

The model should not need another `todo` read just to discover the next item.

# 3. Canonical Markdown representation

The public representation of a todo list is Markdown-like text.

Use:

```text
- [ ] pending
- [>] in progress
- [x] done
- [!] blocked
- [~] dropped
```

Example:

```text
TODO · 2 active · 3 pending · 1 blocked · 1 dropped · 4 done

- [ ] #1 Implement todo extension
  - [x] #2 State model
  - [>] #3 Markdown synchronization
  - [ ] #4 Durable integration
    - [!] #5 Verify reopen — fixture unavailable
  - [>] #6 Spinner presentation
  - [~] #7 Experimental widget
  - [ ] #8 Final verification
```

Use exactly two spaces per nesting level.

IDs are stable positive integers.

The header is generated by the tool; it is not part of structural Markdown input.

The model-facing `todo({})` call should always return the **entire list**, including closed items.

Do not paginate.

Instead, impose a sensible hard upper bound on list size.

Recommended v1 bounds:

```text
maximum items:       128
maximum depth:       8
maximum task text:   200 Unicode characters
maximum blocker:     300 Unicode characters
```

This lets the public API remain simple and unpaginated.

# 4. Structural synchronization

`markdown` is not a sequence of CRUD operations.

It means:

> "Make the todo hierarchy structurally look like this document."

Example existing state:

```text
- [ ] #1 Implement todo extension
  - [x] #2 State model
  - [>] #3 Durable integration
```

The model may submit:

```text
- [ ] #1 Implement todo extension
  - [x] #2 State model
  - [>] #3 Durable integration
    - [ ] Add reopen regression test
  - [ ] Spinner presentation
```

The extension should infer everything:

* `#1`, `#2`, `#3` retain their identities;
* their text may be edited;
* indentation determines parent relationships;
* order in the document determines sibling order;
* the two new rows receive new monotonically allocated IDs;
* unchanged IDs preserve their statuses;
* omitted IDs are removed from the resulting tree;
* moved IDs move with their entire subtree semantics;
* no explicit `move` operation exists.

The agent never manipulates `parent_id`.

## Existing IDs

When an existing ID appears in structural Markdown:

* preserve the ID;
* preserve its current status;
* preserve its blocker reason where applicable;
* use the Markdown for text, position and hierarchy.

Status markers on lines carrying existing IDs are display hints only during structural synchronization.

Structured `updates` are the authoritative mechanism for changing status.

This avoids having two competing status-mutation protocols.

## New items

New todo rows omit an ID:

```text
- [ ] Add durable reopen test
```

They must use the pending marker:

```text
[ ]
```

The extension allocates IDs in deterministic document order.

Reject a new line using `[x]`, `[!]`, `[>]`, or `[~]`; tell the model to create it as pending and use a status update if necessary.

## Unknown IDs

If structural Markdown supplies:

```text
#999
```

and that ID has never existed in current state, reject the entire synchronization.

The model cannot manufacture IDs.

Deleted IDs are not reused.

## Empty Markdown

Allow:

```json
{"markdown": ""}
```

to clear the todo list.

`next_id` must remain monotonic; clearing the list does not reset it within the durable session.

---

# 5. Markdown parser invariants

The parser and tree normalization live in Luau.

Reject:

* tabs for hierarchy;
* odd-numbered indentation;
* indentation jumps greater than one level;
* duplicate IDs;
* unknown IDs;
* malformed todo markers;
* empty task text;
* excessive depth;
* excessive item count;
* control characters unsafe for terminal display;
* bidi control characters;
* malformed UTF-8/state representations where relevant.

Normalize ordinary whitespace conservatively.

Do not silently repair an ambiguous tree.

Return a concise model-visible error and preserve the old durable state exactly.

Structural synchronization is atomic.

# 6. Private durable representation

The public Markdown representation is not the durable schema.

Internally store normalized structured state under:

```text
todo.state.v1
```

Conceptually:

```json
{
  "next_id": 9,
  "items": [
    {
      "id": 1,
      "text": "Implement todo extension",
      "status": "pending"
    },
    {
      "id": 2,
      "text": "State model",
      "status": "done",
      "parent_id": 1
    },
    {
      "id": 3,
      "text": "Durable integration",
      "status": "in_progress",
      "parent_id": 1
    }
  ]
}
```

Optional:

```text
parent_id
reason
```

Array order is canonical display/sibling order.

Do not add another explicit ordering field unless implementation proves it necessary.

IDs:

* begin at 1;
* increase monotonically;
* never change;
* never reuse.

# 7. Status-update semantics

A status update looks only like:

```json
{
  "id": 5,
  "status": "done"
}
```

or:

```json
{
  "id": 5,
  "status": "blocked",
  "reason": "waiting for upstream fixture"
}
```

Multiple updates in one call are atomic and applied in array order.

The extension owns all recursive consequences.

The model does not.

## `done`

Setting a todo to `done` means the outcome represented by that subtree is complete.

For the target and its descendants:

```text
pending      -> done
in_progress  -> done
blocked      -> done
done         -> done
dropped      -> dropped
```

An explicitly dropped descendant stays dropped.

## `blocked`

Setting a node to blocked applies to currently open work in its subtree:

```text
pending      -> blocked
in_progress  -> blocked
blocked      -> blocked
done         -> done
dropped      -> dropped
```

Store the supplied reason on the target.

Reason is optional but encouraged.

Blocked tasks are never automatically promoted.

## `dropped`

Setting a node to dropped recursively abandons currently open work:

```text
pending      -> dropped
in_progress  -> dropped
blocked      -> dropped
done         -> done
dropped      -> dropped
```

This means "intentionally removed from scope", not "successfully finished."

## `pending`

`pending` is the explicit reopen/reset state.

When applied to a node:

* target becomes pending;
* closed/blocked descendants become pending;
* closed ancestors are reopened to pending;
* blocker reasons in the reopened subtree are cleared.

This is intentionally strong and replaces a separate `reopen` operation.

## `in_progress`

When applied to a node:

* target becomes `in_progress`;
* completed/dropped/blocked ancestors become `pending`;
* target blocker reason is cleared;
* descendants are otherwise unchanged.

Allow multiple independent `in_progress` todos.

Tea may have parallel/delegated work.

Do not impose OMP's global single-active-task invariant.

# 8. Automatic next-task selection

The extension should reduce bookkeeping further.

After every successful state-changing call:

1. determine whether any todo is `in_progress`;
2. if at least one exists, do nothing;
3. otherwise find the first actionable `pending` leaf in canonical depth-first document order;
4. promote it automatically to `in_progress`.

Never auto-promote:

* blocked work;
* dropped work;
* done work;
* a non-leaf whose actionable child should be performed first.

When a new plan is created, this should automatically make the first leaf active.

When the active leaf is completed, blocked, or dropped, the next leaf automatically becomes active.

This should cover the normal coding-agent workflow without explicit `start` calls.

The model can still explicitly switch or parallelize by setting another ID to `in_progress`.

# 9. Mutation results

Do not echo the entire todo list into model context after every status change.

Status mutations should return concise information:

```text
Completed #4 and 2 descendants.
Next: #7 Durable reopen test
TODO · 1 active · 4 pending · 0 blocked · 0 dropped · 6 done
```

For multiple updates:

```text
Updated 3 todos.
Next: #7 Durable reopen test
TODO · 2 active · 3 pending · 1 blocked · 0 dropped · 6 done
```

Structural synchronization should return the complete canonical Markdown because the model needs to learn IDs assigned to new rows.

A read call returns complete canonical Markdown.

Thus:

```text
read            -> full state
structural sync -> full state
status updates  -> compact result + next actionable item
```

# 10. THE IMPORTANT UI FEATURE: todo state owns the live spinner presentation

This is a core requirement, not an optional polish item.

Every invocation of the `todo` tool must transparently refresh Tea's live activity/spinner presentation with the current todo list.

The model must not call a second UI tool.

The extension must not request a separate widget.

The agent simply calls `todo`, and the human UI updates.

The intended experience is roughly:

```text
• ⠹ Todo · 1 active · 3 pending · 1 blocked
  - [ ] Implement todo extension
    - [x] State model
    - [>] Durable integration
      - [!] Reopen test
    - [ ] Spinner integration
    - [ ] Verification
```

Then the model continues reasoning, reading files, editing, running tests, etc., while this remains the current mutable activity presentation.

When the model later calls:

```json
{
  "updates": [
    {"id": 3, "status": "done"}
  ]
}
```

the same spinner/activity area immediately becomes:

```text
• ⠸ Todo · 1 active · 2 pending · 1 blocked
  - [ ] Implement todo extension
    - [x] State model
    - [x] Durable integration
      - [!] Reopen test
    - [>] Spinner integration
    - [ ] Verification
```

This is the primary human-visible todo UI.

No persistent widget is necessary.

# 11. Implement spinner updates GENERICALLY

Do **not** special-case `tool_name == "todo"` in the TUI.

Do not make `AppState` understand todo JSON.

Do not make the renderer query extension state.

Instead, add a tiny generic presentation capability to Luau-backed tools.

Tea already has:

```text
ToolUpdateSink
ToolUpdate
AgentEventKind::ToolExecutionUpdate
```

and Luau tool execution already has access to the tool update sink.

Use that path.

## Preferred generic design

Extend:

```rust
pub struct ToolUpdate {
    pub content: String,
    pub details: Option<SerializedJson>,
}
```

with a typed presentation field approximately like:

```rust
pub activity: Option<String>
```

Do not smuggle this through magic prefixes in `content`.

Do not make the TUI parse `details_json` conventions such as:

```text
{"todo": ...}
```

The core concept is generic:

> a running tool may replace the transient human-visible activity text for the current agent operation.

`activity` is:

* presentation-only;
* non-durable;
* not model context;
* not an effect;
* not authority;
* not part of extension state;
* not written into scrollback.

# 12. Luau handler update yield

Today a resumable Luau handler yield represents a capability call.

Generalize the runtime slightly so a handler can also yield a presentation update.

Support something approximately like:

```lua
coroutine.yield({
    kind = "update",
    activity = activity_text,
})
```

Optionally support:

```lua
coroutine.yield({
    kind = "update",
    content = "ordinary progress",
    activity = activity_text,
})
```

Semantics:

### `kind = "capability"`

Existing behavior stays byte-for-byte/semantically compatible.

### `kind = "update"`

* does not invoke a host capability;
* emits a generic `ToolUpdate`;
* immediately resumes the Luau coroutine;
* carries no filesystem/network/state authority;
* does not count as an `extension.state` operation;
* does not become a model-visible result.

Bound repeated update yields using an existing finite handler ceiling rather than leaving an unbounded host-update loop possible.

A reasonable v1 implementation is to count all externally observable coroutine yields against one finite per-invocation yield budget derived from the existing handler limits.

Also bound activity payload size, e.g. 8 KiB UTF-8.

Do not add a broad extension UI framework.

This one tiny primitive is enough.

# 13. AppState activity override

Add presentation-only state approximately like:

```rust
activity_text: Option<String>
```

to `AppState`.

When:

```text
ToolExecutionUpdate.activity = Some(...)
```

arrives:

```text
activity_text = Some(...)
```

The activity survives:

* completion of that individual tool call;
* subsequent model thinking;
* subsequent ordinary tool calls;

for the rest of the current root operation.

An unrelated tool update with no `activity` field must **not** clear it.

The next todo call replaces it.

Clear it when a new independent root operation begins or when the current operation is abandoned/replaced.

It is not durable.

A reopened session does not magically have activity text until the active agent invokes `todo` again.

That separation is correct:

```text
todo.state.v1 = durable semantic state
activity_text = disposable terminal projection
```

# 15. Bound spinner size without involving the model

The model-facing `todo({})` read always returns the complete todo tree.

The spinner projection is human UI and may be bounded separately.

Do not let a pathological 128-item plan consume the entire terminal.

The extension should generate a compact activity projection from the same state.

Recommended:

* first line: aggregate counts;
* show all open items when reasonably small;
* hard cap at approximately 12 visible todo rows;
* always retain every `in_progress` item before ordinary pending rows;
* prefer open/blocked work over completed/dropped history;
* if rows are omitted, end with:

```text
  … 7 more
```

The activity view does not need IDs for human usability, but reusing canonical rows with IDs is acceptable if it materially simplifies the Luau formatter.

Do not let this display-selection policy leak into the model tool schema.

From the model's perspective there is still just one todo state.

# 16. Every todo call publishes activity

This invariant should be tested explicitly.

Every `todo` invocation should:

1. load current `todo.state.v1`;
2. validate it;
3. perform the requested operation, if any;
4. persist the new state if mutated;
5. compute canonical current todo state;
6. compute bounded activity presentation;
7. emit generic Luau `kind = "update"` with that activity;
8. return the model-facing result.

This includes:

```text
todo({})
todo({markdown=...})
todo({updates=...})
```

If a requested mutation is invalid but the previous durable state was successfully loaded, it is acceptable—and preferable—to republish the unchanged valid todo activity before returning the error.

If durable state itself is corrupt, do not pretend the todo list is empty. Return a bounded error.

# 21. Compaction

Todo durability should be independent of model context.

Do not inject the entire list after every turn.

Do not use `goal`'s `on_idle` continuation pattern.

Todo state should never itself create another agent turn.

The static prompt should simply teach:

> Todo state is durable and may survive context you no longer see. On resuming substantial tracked work, after compaction, or when unsure of the current plan, call `todo` with no arguments instead of reconstructing the plan from memory.

Because `todo({})` also refreshes the spinner, one read restores both:

* model awareness;
* human activity presentation.

That is a particularly clean property of this design.

# 22. Prompt guidance

Keep `prompts.luau` short.

Something approximately equivalent to:

```text
Todo extension

Use `todo` for substantial multi-step work or explicit user checklists.

Call `todo` with no arguments to read the complete durable plan.

Use `updates` to report status changes. The extension handles hierarchy,
recursive transitions, and automatic next-task selection.

Use `markdown` only to create or restructure the plan. Preserve existing
#IDs when editing returned Markdown; omit an ID for a new task.

Keep tasks concise and outcome-oriented. Mark work done immediately after

dependency; drop work only when intentionally removing it from scope.

```

Do not teach internal tree mechanics.

That is the tool's job.

# 23. Interaction with explicit user plans

When the user supplies a concrete checklist or numbered set of work items, the model should preserve the material items rather than compressing them away.

Nested Markdown should make this natural.

For example, a user asking for:

- [ ] Tests

Plan generation remains model reasoning.

Todo *management* belongs to the tool.

# 28. Subagent ownership

For v1, the todo state is root-agent coordination state.

Do not make independently executing child agents mutate one shared todo snapshot concurrently.

That risks:

```text
read old state
child A writes
child B writes from old state
lost update
```

The root agent owns the plan and updates statuses as delegated work progresses.

Do not introduce:

* locks;
* transactions across agents;
* CRDTs;
* shared todo service;
* subagent todo RPC.

If child harnesses currently inherit every global builtin, make the smallest clean distinction necessary so mutable todo ownership remains root-only.

Do not disturb existing goal/subagent behavior.

### Persistence during operation

After the todo tool settles:

* its ordinary transcript/tool row can settle normally;
* the activity remains visible;
* subsequent assistant thinking retains it;
* unrelated tools do not clear it.

### Replacement

A later activity update atomically replaces the previous activity.

### New operation

Starting a separate root operation clears stale presentation until something publishes a new activity value.

### Scrollback

Activity rows never become part of the stable scrollback prefix.

This matters greatly given Tea's scrollback-native TUI architecture.

### Resize

Resizing reflows the mutable activity presentation normally without touching historical committed rows.

### Tiny terminal

Activity may be clipped before the composer is lost.

The composer remains usable.

# 31. Todo Luau behavioral tests

Use Tea's existing Luau extension test machinery.

Cover at minimum:

## Empty state

```text
todo({})
```

returns an empty-list representation and publishes empty/cleared todo activity appropriately.

## Initial plan

Input:

```text
- [ ] Root
  - [ ] Child A
  - [ ] Child B
```

allocates deterministic IDs.

First leaf automatically becomes active.

## Read

Returns full canonical Markdown with IDs and statuses.

## Structural append

Returned Markdown can be edited by adding an ID-less row.

Existing IDs remain stable.

New row gets next monotonic ID.

## Rename

Changing text next to an existing ID preserves ID/status.

## Reorder

Moving a line within its siblings changes canonical order.

## Reparent

Changing indentation changes hierarchy.

## Delete

Omitting an existing row removes it.

Its ID is never reused.

## Invalid indentation

Rejected atomically.

## Unknown ID

Rejected atomically.

## Duplicate ID

Rejected atomically.

## Excessive depth/count/text

Rejected atomically.

## Status preservation during Markdown sync

Changing `[x]` to `[ ]` in structural Markdown for an existing ID must not silently reopen it.

Structured `updates` remain the authority.

## Done recursion

Parent completion closes open descendants.

Dropped descendants remain dropped.

## Block recursion

Open descendants block.

Closed descendants remain closed.

## Drop recursion

Open descendants drop.

Done descendants remain done.

## Reopen

`pending` recursively reopens the target subtree and its necessary ancestors.

## Start

`in_progress` reopens necessary ancestors.

## Multiple active

Multiple independent active items are valid.

## Auto promotion

When the final active item closes, first pending actionable leaf is promoted.

## Atomic update array

If update N is invalid, updates 1..N-1 do not persist.

## Block reason

Persists and appears in reads/activity.

## Corrupt state

Produces an error.

Never silently resets to empty.

# 36. Design quality bar

Optimize heavily for the model-facing contract.

If implementation complexity can move from the model schema into deterministic Luau code, move it.

A model should not need examples explaining twelve operations.
